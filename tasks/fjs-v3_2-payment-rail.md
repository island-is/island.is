## Review: what the v3_2 payment endpoints give us

Not a task list yet — a survey of the gap between the new FJS endpoints and the existing
island.is payment rail.

### Usable as-is

1. `payID` per debt. The backend already maps it (`pay-debts.service.ts:32`); it is sitting in
   `externalData` unused. Only the frontend `CustomerDebt` type is missing it.
   **FJS have since confirmed `payID` is required on the payment call** — each `payDebts[]` line
   must carry the `payID` of the debt it settles, so this field is no longer optional plumbing:
   it has to survive from `GetDebtsApi` all the way into the settlement payload.
2. `payInfo` is field-for-field what the payments service already builds for card payments —
   `PAN`, `RRN`, `authCode`, `cardType`, `payableAmount`, `paymentMeans`, `correlationId`
   (`cardPayment.utils.ts:339-349`). FJS reused their own DTO, so no new mapping is needed.
3. `payFlowId` lines up with `paymentFlow.id`, which the charge path already sends as
   `requestID` (`utils/fjsCharge.ts`).
4. `/validatePayment` slots into the same place as the existing catalog pre-flight
   (`paymentFlow.service.ts:290 chargeFjsV2ClientService.validateCharge`).
5. `payDebtPost3` / `validatePaymentPost4` are already generated in the client — they only need
   wrapper methods on `FinanceClientV3Service`.

### The structural mismatch

The whole rail is catalog-keyed. `payment_flow_charge` stores `chargeType` + `chargeItemCode`
(`paymentFlow.model.ts:63,71`), `PaymentService.createCharge` resolves items against the FJS
catalog (`payment.service.ts:271`), and the worker prices from the catalog again at settlement
(`worker.service.ts:196`). Debts have no catalog item — that is the same wall the
`chargeTypeId`-as-`chargeItemCode` TODO in `template.ts` hit.

`/payDebt` is the debt-shaped sibling of `chargeFjsV2.createCharge`, so the fix is a second
settlement target at one seam, not a catalog workaround:

    worker.service.ts:162  createFjsChargeForPaymentFlow
      → buildCardChargePayload        (catalog + payInfo → chargeFjsV2)
      → buildDebtPaymentPayload       (payDebts + payInfo → financeV3.payDebt)   ← new

Field mapping is 1:1: `requestID`→`payFlowId`, `payeeNationalID`→`nationalId`,
`charges[]`→`payDebts[]`, `effictiveDate`→`paymentDate`, `payInfo`→`payInfo` unchanged.
Each `payDebts[]` entry is `{ payid, payAmount }` (`finance-v3/gen/fetch/types.gen.ts:211`), so the
per-line identifier FJS wants is `payid` — not a charge code.

The `payID` requirement is what makes the catalog detour unworkable rather than merely awkward.
A `payment_flow_charge` row can hold `chargeType` + `chargeItemCode` and nothing else
(`paymentFlow.model.ts:63,71`), so a flow built the catalog way has nowhere to put `payID` and the
worker has nothing to send. Smuggling `payID` through `chargeItemCode` is not an option — that
column is what `PaymentService.createCharge` resolves against the FJS catalog
(`payment.service.ts:271`) and what the worker re-prices from at settlement
(`worker.service.ts:196`). The flow has to carry the debt lines themselves.

### Work, by layer

Template (small, independent, unblocks the rest) — DONE:

- ~~`payID` onto `CustomerDebt` and `SelectedDebt`~~ — done; `getSelectedDebts` now emits
  everything needed to build `{ payid, payAmount }`.
- ~~`debtsSignature` should include `payID`~~ — done; a debt whose `payID` moved invalidates
  the answers instead of paying against a dead identifier.
- The payment overview keys its lines by `payID` (`paymentSection.ts`), replacing the
  `${chargeTypeId}-${index}` workaround. Display-only — it does not reach FJS.
- `template.ts` `chargeItems` stays wrong until the rail exists — do not "fix" it in place.

client (`libs/clients/finance-v3`) — DONE:

- `FinanceClientV3Service.payDebt(user, PaymentsInDt)` and `.validatePayment(user, ValidatePaymentsInDt)` wrap the generated `payDebtPost3` / `validatePaymentPost4`.
  Both use `data()` rather than `dataOr404Null()` — a settlement must not swallow a 404 into a
  silent `null`. `payDebt` casts its response because `/payDebt`'s documented 200 has an empty
  body, so the generated union collapses to `unknown`; `null` means "no receipt", not "failed".
- Payload types (`PaymentsInDt`, `ValidatePaymentsInDt`, `PayInfo`, `PayidDetailsDt`, both Out
  DTOs) are exported from the client index so a caller can build a request.
- `bigint` on `totalAmount` / `payAmount` / `payableAmount` is safe — the generated
  `jsonBodySerializer` stringifies bigints rather than throwing.
- Note the layering: `financeV3.service.ts` is hand-written and git-tracked; `gen/fetch/**` is
  generated by `@hey-api/openapi-ts` and gitignored (`.gitignore:87`). Regenerating never adds
  service methods — a new endpoint stays invisible until someone writes the wrapper.

payments service (the actual work):

- Carry debt lines on a flow (new table, or a `payDebts` column) instead of catalog charges —
  `payID` per line is now a hard requirement, not a nice-to-have.
- Bypass catalog resolution/validation for those flows.
- Worker branch to `/payDebt`; pre-flight through `/validatePayment`.
- `.xroad(Base, Client, ChargeFjsV2)` in `apps/services/payments/infra/payments.ts:167,188`
  needs `Finance` added — see below. Not done yet, deliberately deferred.
- Auth: the finance-v3 client is `authSource: 'context'` with token exchange
  (`financeV3.module.ts`). The worker is a scheduled job with no user context, so calling
  `payDebt(user, ...)` from it needs a machine-auth path. Unsolved.

#### The `Finance` xroad entry — what it is and why it bites

`.xroad(...)` is not a network ACL. `infra/src/dsl/dsl.ts:231` only appends config blocks; each
`XroadConf` is a bundle of env vars injected into the container. `Base` gives `XROAD_BASE_PATH`
(the security server URL); `Finance` (`infra/src/dsl/xroad.ts:218`) gives the service paths,
including `XROAD_FINANCES_V3_PATH` (`IS-DEV|IS-TEST|IS` `/GOV/…/FJS-Public/financeServicesFJS_v3`).

`FinanceClientV3Config` reads it with `env.required('XROAD_FINANCES_V3_PATH', 'IS-DEV/…')` and
`FinanceClientV3Module` builds `${xRoadBasePath}/r1/${xRoadServicePath}`. Without `Finance` in the
list the var is never injected.

The trap is the fallback. `ConfigurationLoader.required()` (`libs/nest/config`, line 120) returns
the dev fallback only when `allowDevFallback`, which is `process.env.NODE_ENV !== 'production'`
(line 15). So registering `FinanceClientV3Module` in the payments service without the infra change:

- dev/staging — silently falls back to the hardcoded `IS-DEV/…` path and looks fine;
- prod — no fallback, missing-variable issue, **boot fails**.

A deploy-time failure in the only environment that matters, so do it in the same change as the
module registration, not after.

Both entries need it, not one: `payments.ts:167` (the service) and `:188` (the scheduled worker)
each carry their own `.xroad(Base, Client, ChargeFjsV2)`. The worker is where `/payDebt` is
called; a `/validatePayment` pre-flight would sit in the service.

Caveat: this is configuration only. X-Road also requires the payments subsystem to be authorized
on the FJS side for `financeServicesFJS_v3`. The env vars say where to aim; whether the security
server accepts the call is a separate grant — confirm with FJS before assuming a green deploy
means a working call.

### Ask FJS before building

- `paymentOptions` is an untyped `string` — what are the values?
- `paymentDate` format (the charge API uses `yyyy-MM-dd`).
- No cancel/refund counterpart to `deleteCharge(paymentFlowId)` (`paymentFlow.service.ts:1124`).
- `/payDebt` documents 200 (empty), 201 and 202 — which means what?
- ~~Does the payment call need `payID`?~~ Answered: yes, `payID` goes with the payment.
- Still open: how long is a `payID` valid? If it can change between fetching debts and paying,
  we need to know whether `/validatePayment` is the intended guard (for a stale `payID` as well
  as a stale amount) and what the failure looks like when it has gone stale.

## Measured against IS-DEV (2026-09-10)

Called `/validatePayment` directly through the local X-Road proxy (`yarn proxies xroad`,
`localhost:8081/r1/IS-DEV/GOV/10021/FJS-Public/financeServicesFJS_v3`) as
`0101307789` (Gervimaður Útlönd, 278 debts). `/payDebt` was **not** called — it settles.

### `paymentOptions` — answered

Semicolon-separated list of permitted payment means, **not** a valid/invalid verdict:

    "CARD;TRANSFER"   totalAmount <= 300000
    "TRANSFER"        totalAmount >  300000

Threshold binary-searched exactly: 300.000 kr → `CARD;TRANSFER`, 300.001 kr → `TRANSFER`.
It keys off `totalAmount` only — 2 × 150.000 keeps CARD, 2 × 200.000 loses it, and 50 debts
at 1 kr keeps it. Identical for all 13 `chargeTypeId`s this persona has
(AB SJ VA HB AY SA HA UF HK VE GN DS YG), so it is amount-driven, not charge-type-driven.

Maps onto `payInfo.paymentMeans`: `CARD` → `Kreditkort`/`Debetkort`, `TRANSFER` → `Milli`.
So the card ceiling has to gate the payment-means picker in the UI: above 300.000 kr,
card must not be offered.

### It does not validate amounts

Partial, overpay, zero and **negative** `payAmount` all return 200 `CARD;TRANSFER`:

| case                           | result            |
| ------------------------------ | ----------------- |
| full debt (219.683 of 219.683) | 200 CARD;TRANSFER |
| partial (100.000 of 219.683)   | 200 CARD;TRANSFER |
| 1 kr                           | 200 CARD;TRANSFER |
| overpay (300.000 of 219.683)   | 200 CARD;TRANSFER |
| 0 kr                           | 200 CARD;TRANSFER |
| −500 kr                        | 200 CARD;TRANSFER |

So **paying an arbitrary amount is allowed by the API** — nothing requires a debt to be
settled in full. Amount sanity (non-negative, not above the debt, minimum) is ours to enforce;
`/validatePayment` will not do it.

Negatives re-verified five ways (2026-09-10), all 200 `CARD;TRANSFER`: a single −500 line, the
exact inverse of the debt (−219.683), and −999.999.999. The last one still offers `CARD`, which
shows the ceiling is a bare `totalAmount <= 300000` upper bound with no lower bound.

**The `totalAmount == sum` rule is not a safety net.** Mixed payloads pass it while carrying a
negative line — `+100.000` with `−500` (total 99.500) and `+100.000` with `−100.000` (total 0)
both returned 200. Since the rule only compares the total against the sum of the lines, deriving
`totalAmount` by summing them makes code 5 unreachable by construction. It catches a mismatch we
introduce ourselves, not a bad line. Bound `payAmount` where the payload is built, not only in
the UI.

Caveat on all of the above: this is `/validatePayment` only. `/payDebt` was never called, so
whether the settlement endpoint would actually post a negative or zero amount is **unknown** —
add it to the FJS questions rather than assuming either way.

### The one amount rule it does enforce

`totalAmount` must equal `sum(payDebts[].payAmount)`. Violating it gives code 5, whose
Icelandic text is misleading — it says "fjárhæð skulda" (the debt amount) but it actually
compares the total against the sum of the lines, which is why a consistent partial payment
passes. Empty `payDebts` and a missing `totalAmount` both trip the same code.

### Error codes (`title` is a numeric code as a string)

| `title` | HTTP | `detail`                                            | trigger                                             |
| ------- | ---- | --------------------------------------------------- | --------------------------------------------------- |
| `2`     | 400  | `Kennitala finnst ekki <nid>`                       | national ID unknown to FJS (also for malformed IDs) |
| `3`     | 400  | `Reikningur <payid> finnst ekki`                    | unknown/stale `payID`                               |
| `5`     | 400  | `Samtals greiðsla stemmir ekki við fjárhæð skulda.` | `totalAmount` ≠ sum of `payAmount`                  |
| `10`    | 400  | `Gildisdagur ekki á formati YYYY-MM-DD)`            | bad `paymentDate`                                   |

**The spec is wrong about the error envelope.** It documents only 200/401 for
`/validatePayment` and puts errors inside `validatePayment_POST_response.error` as
`ProblemDetails_DT`. Reality: HTTP **400** with a bare `{title, status, detail}` object at the
root — no `error` wrapper, no `errors[]`, no `param`, and `title` is a code rather than the
"short human-readable summary" the spec promises. `data()` in `financeV3.service.ts` will throw
on these, and the code/`detail` need extracting by hand if we want to map them to user messages.

### Answers to the other open questions

- **`paymentDate` format** — `YYYY-MM-DD` confirmed (code 10 states it). Past (2020-01-01) and
  future (2027-12-31) dates are both accepted; no range check.
- **Stale `payID`** — yes, `/validatePayment` is a usable guard: an unknown `payID` fails with
  code 3 naming the offending id. Still unknown is _when_ FJS rotates a `payID`.
- **Not enforced** — duplicate `payid` in one payload (200), and a missing `payFlowId` (200).
  Do not rely on FJS to reject either.

### Two incidental findings

- **`payID` can be composite.** Charge type SA came back as `88204854!88204855`. Treat `payID`
  as an opaque string — never split, parse, or put it in a URL path unescaped.
- **The worker's machine-auth problem is solvable.** A plain `client_credentials` token for
  `@island.is/clients/dev` with scope `@fjs.is/finance` is accepted by FJS and reads any
  kennitala's debts — the token carries no `nationalId`/actor claim at all. So the scheduled
  worker does not need a user context to reach `/payDebt`; it needs its own machine client with
  that scope. Corollary: FJS does not _require_ user context to serve a kennitala's debts, so
  the per-person authorization check has to be ours. (Precisely: a token carrying no user claim
  was accepted. Whether FJS validates the subject when a user token _is_ present — the
  `tokenExchange` path the app actually uses — was not tested.)
- Payload size is not a concern: all 278 debts in one call (12 KB) validated fine.
